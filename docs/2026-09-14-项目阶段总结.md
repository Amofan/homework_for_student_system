# 初中数学作业分析系统阶段总结

## 一、课题定位

课题名称建议使用：**基于知识点画像与大模型辅助反馈的初中数学作业分析系统设计与实现**。

系统面向初中数学教师，解决结构化答案批量整理、客观题自动评分、解答题过程性反馈、教师复核和学情统计相互割裂的问题。项目不追求让大模型代替教师，而是采用“确定性规则 + 大模型建议 + 教师确认”的人机协同路线。

## 二、当前已经形成的完整闭环

```text
教师登录与数据隔离
        ↓
班级、学生、知识点和题库维护
        ↓
创建作业并导入 Excel 答案
        ↓
客观题规则评分 / 解答题 AI 建议
        ↓
教师采纳、修改或驳回
        ↓
按已确认结果生成知识点画像和错因统计
```

当前代码已覆盖以下功能：

- JWT 登录、BCrypt 密码校验和教师数据隔离；
- 班级与学生名册管理；
- 七至九年级知识点、题库、可接受答案和过程评分项；
- 作业创建与 `.xlsx` 答案导入；
- Excel 表头、公式单元格、未知编号、重复答案和整批回滚校验；
- 单选题、填空题的确定性规则评分；
- 解答题 AI 任务、Responses 风格模型适配器、JSON Schema 结构化输出校验和有限重试；
- 教师采纳、修改、驳回以及复核审计；
- 只基于已确认结果的知识点掌握度和高频错因统计；
- Vue 中文教师端、演示数据、响应式布局和主流程浏览器测试。

## 三、当前技术实现

| 层次 | 当前实现 |
| --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus、ECharts、Pinia、Vue Router |
| 后端 | Java 21、Spring Boot 4.1.1、Spring Security、Spring JDBC |
| 数据 | MySQL 8.4 作为正式数据库，H2 用于演示和测试，Flyway 管理 6 个迁移版本（V1–V6） |
| 文件 | Apache POI 解析 Excel |
| AI | 后端直调大模型 API，不使用 RAG、向量数据库和 OCR |
| 测试 | JUnit、MockMvc、Vitest、Playwright |

大模型输入只包含匿名答案编号、题目、标准答案、学生作答、评分项和错因标签，不包含姓名、学号、班级名称、JWT 或模型密钥。模型结果只是待复核建议，不能直接进入正式统计。

## 五、当前最有价值的部分

1. **需求真实**：教师确实需要批量处理作业、定位共性错因并保留人工最终决定权。
2. **技术组合合理**：传统规则负责确定性内容，大模型只处理开放性解答，避免把所有问题都交给模型。
3. **师范特色明确**：知识点画像、过程评分、错因反馈和教师复核都直接对应教学评价过程。
4. **论文可实验**：可以比较 AI 建议与教师评分之间的误差、错因识别效果、教师修改率和节省时间。
5. **边界适合毕设**：不增加 RAG、OCR、学生端和微服务，工作量可控，核心创新点仍然成立。

## 六、主要不足与风险

### 最高优先级

- 后端全量测试的数据清理策略不统一；
- Vitest 与 Playwright 的文件收集范围冲突；
- 当前真实 MySQL 和真实模型都没有本轮运行证据。

### 功能完整性

- 分层练习生成、教师确认和 Word 导出尚未实现；
- AI 任务领取还缺少更严格的并发竞争保护；
- 题库尚未记录难度，无法稳定支持分层选题；
- 离线评测脚本和人工标注样本尚未建立。

### 工程质量

- 前端 ECharts 和 Element Plus 产物偏大，需要按需加载；
- 部分集成测试重复编写数据库清理 SQL；
- H2 版本高于当前 Flyway 已验证版本，虽不阻塞运行，但会产生兼容性警告；
- 当前仓库尚未产生正式提交，所有新增文件仍需在最终交付前统一审查。

## 九、第二轮补充：论文取数能力与真实模型验证

验证日期：2026 年 9 月 15 日（晚于第八节）。这一轮做的不是新功能，
而是把"论文要引用的数字从哪来"这条路打通：此前评测脚本的输入只能靠手工整理，
系统里也没有任何地方记录模型耗时、令牌用量和教师复核耗时。

### 9.1 补上的取数字段（Flyway V7）

`grading_result.ai_error_type`、`ai_grading_task.input_tokens / output_tokens / ai_seconds`、
`teacher_review.teacher_seconds`。全部可空。

其中 `ai_error_type` 是必需的：教师复核会覆盖 `grading_result.error_type`，
覆盖之后模型当初判成什么就再也查不回来，而"错因一致率"正是要评测的指标之一。

模型耗时只量一次 HTTP 交换（解析与校验不计入）；用量取自响应体的 `usage` 块，
缺失时记 null 而不是 0——"没有数据"和"没花令牌"混在一起会让统计失真。

### 9.2 取数路径

教师界面在选中待复核项时开始计时（`performance.now()`，单调时钟，不受系统对时影响），
确认时把秒数随复核请求提交。取数用新增的导出接口：

```text
GET /api/evaluation/assignments/{assignmentId}/grading-cases.csv
```

导出的是**已复核的模型评分样本**，列名与 `evaluation/evaluate_grading.py` 的输入契约一致，
可原样喂给脚本，不需要任何手工整理。接口按作业归属鉴权，导出物只含匿名编号。

评测脚本新增中位数口径（`teacher_median_seconds`、`ai_median_seconds`）。
加它的原因是用时分布不对称：教师中途去忙别的事会留下一个几十分钟的离群值，
把均值整体拉高，而中位数不受影响。两个口径并列输出，均值有没有被带偏一眼可见。
原有的 `estimated_saving_ratio` 仍按均值计算，没有改口径，避免同一个数字在论文前后不一致。

### 9.3 同时修复的两个缺陷

- **演示配置把环境变量彻底压掉**：`application-demo.yml` 里写死的 `app.model.*` 字面量
  优先级高于 `application.yml` 的 `${MODEL_ENABLED:...}` 占位符，
  导致按文档设置 `MODEL_*` 环境变量后仍然走"模型未启用"分支，
  失败还在 0.1 秒内返回，看起来像网络问题。改为 profile 只提供默认值、覆盖入口留给环境变量。
- **失败原因被吞掉**：`AiGradingTaskWorker` 把所有异常统一映射成同一条对外消息，
  却不记录 cause，配置错误、连接失败与响应解析失败在外部完全无法区分。
  现在按任务记录一条 WARN（含异常链），异常链不含密钥与响应体。
